## 审查检查表

1. **重复检测须可审计且结论唯一**：按错误信息、关键词、代码区域和触发条件检索；列出候选异同与边界。不能同时写“未发现”和“可能重复”。非同根因、不同修复路径不应误标重复。
2. **分类—标签—动作一致**：修复已有行为归 `bug`，不混 `enhancement`；功能已存在归 `question`+`documentation`；垃圾 Issue 归 `other`+`invalid` 并关闭。先核验仓库真实标签，区分语义建议与可实际添加。
3. **优先级看影响范围**：审核绕过、漏报、误罚和核心配置失效偏 `high`；兼容问题须确认工具是否默认注册、是否导致全部请求失败及是否有绕过，勿仅因 HTTP 400 判 `critical`。
4. **方案分层并推荐低风险起点**：明确最小修复、高级方案、测试和环境成本。外部库/LLM 必须超时、限并发、`ImportError` 或默认降级；标题只在模糊时补对象、现象、根因，通常不重复写优先级。
5. **多入口与副作用**：命令、WebUI、后台任务应复用同一业务方法；检查权限、二次确认、审计、状态更新、失败补偿、幂等和并发。远程处罚不得因前端隐藏按钮或内部入口绕过校验。

## 关键技术经验

- **Gemini/AstrBot Schema（ISSUE62）**：严格校验全部工具声明，单个非法 Schema 可能令整次请求 400。数组必须有合法 `items`；优先按工具名称查找，不依赖易变索引。AstrBot 文档可尝试 `list[string]`，但修改 Python 注解前须确认目标版本的 Schema 来源、语法及注解/文档优先级，谨慎使用联合类型。
- Schema 测试应断言所有数组节点含 `items`（元素类型正确），可选 Gemini 冒烟不能作为 CI 唯一保障；区分声明、生成、适配和执行层。
- **异步接口**：含 `yield` 的 `async def` 是异步生成器，调用必须 `async for`；mock 也须保持真实返回协议。
- **审核控制流**：通过词应先于违禁/广告检查；配置关闭只代表该流程不处理，不得无依据提前 `return` 绕过后续审核。完整覆盖开关组合，防止新旧流程重复处罚。
- **审核状态闭环**：持久化的每个状态（如 `ad`/`ok`）都须有查询、路由和动作；确认/放行、撤回、禁言、学习须幂等，部分失败可重试且审计一致。OneBot 撤回约 2 分钟、禁言最小 60 秒，人工审核须考虑时效。
- **唯一关联**：复核操作优先使用消息/审核 ID；群、用户、内容、时间仅辅助。回退候选唯一才自动绑定，0 条或多条均不猜测；可能重复的键用列表而非单值字典，并覆盖并发、过期和重复内容测试。
- **反刷屏/协议**：图片等固定占位符不应因重复被判无用；审核前统一剥离 OneBot 拼接片段，明确非文本消息是否打断短消息窗口。
- **Mixin**：文件归属不等于运行时能力；迁移方法须检查直接/间接依赖、`Main` 继承清单、MRO、所有调用入口及初始化状态。远程审核逻辑优先放 Web 业务层/独立服务层，命令仅委托。

## 仓库模式

- 审核链路通常为 AC 自动机初筛 → LLM 二审 → 撤回/说明，SQLite 保存日志，外置 `lexicon.db` 保存词库。
- 踢人、禁言、撤回、学习等多入口应收敛共享方法；配置、常量和数据库迁移即使只改一行，也要说明旧值兼容性。
- 测试证据须分层：单测、Schema/集成、真实路由、权限失败、平台失败和外部冒烟不可互相替代；“测试数量全过”不能证明唯一性、异步协议或端到端闭环。
