## 1. 审查质量评估

### 覆盖度

本次审查准确识别了核心问题：`Main` 不继承 `CommandsMixin`，因此 WebUI 调用位于 `CommandsMixin` 的 `_recall_ad_review_message` 会失败；将方法迁移至 `WebMixin` 与实际调用链更匹配，方向正确。

但仅凭摘要和变更文件列表，仍可能遗漏以下问题：

- **方法依赖是否完整迁移**：`_recall_ad_review_message`、`_ban_ad_review_user` 可能依赖 `CommandsMixin` 中的其他辅助方法、属性或导入。需要逐项检查其调用的 `self.xxx` 是否在 `Main` 的 Mixin 组合中可用。
- **MRO 与方法覆盖关系**：迁移到 `WebMixin` 后，其他 Mixin 是否也定义同名方法，调用是否落到预期实现。
- **所有调用入口是否覆盖**：WebUI 确认、放行、批量处理、命令入口及后台任务是否仍然使用同一套方法，避免修复 WebUI 后命令路径发生行为变化。
- **异步与异常处理**：撤回、禁言、学习等操作中任一步失败时，审核状态、学习结果和审计日志是否保持一致。
- **权限与审计约束**：迁移后的 WebUI 方法是否仍在调用方之前执行 `_check_remote_operator`、双管理员确认和审计逻辑，而不是形成可绕过的内部操作入口。
- **跨平台兼容性**：禁言与撤回是否继续通过统一的平台适配层执行，而没有依赖命令入口中的额外初始化。

因此，“448 项全过”是积极证据，但如果只是按 `Main` 的 Mixin 组合进行模拟，尚不足以证明真实 WebUI HTTP 路由、权限校验、数据库状态变更和平台操作均完整覆盖。

## 2. 发现的模式

### 代码模式

- 项目采用较多 **Mixin 组合**，通过 `Main` 显式组合能力，而不是让命令模块天然拥有全部 Web 操作。
- 命令入口存在“显式委托”模式：命令不一定通过继承获得实现，而是主动转发到共享逻辑。这种设计可以复用，但容易让调用方误以为方法属于某个 Mixin。
- WebUI 操作具有明显的业务副作用链：审核确认 → 撤回 → 禁言 → 学习 → 更新状态/日志。此类流程需要统一的共享方法，避免命令和 WebUI 各自实现。
- 本次通过删除旧实现、迁移到 `WebMixin` 来消除重复，符合“多入口收敛到共享方法”的项目经验。

### 架构观察

- `Main` 是核心装配点，Mixin 的继承清单实际上构成了运行时 API。新增方法时不仅要看定义位置，还要验证 `Main` 的 MRO 和实例可见性。
- `WebMixin` 不只是 HTTP 路由层，也承载了远程审核操作的业务逻辑。随着功能增多，可能逐渐形成过重的混合层。
- 项目把平台操作、权限、审核状态和 Web 路由关联在一起，功能复用方便，但边界较多，容易产生“方法存在但上下文不完整”的问题。

## 3. 规范完善建议

建议新增或强化以下审查规则：

1. **Mixin 方法迁移规则**  
   迁移方法时必须列出其直接和间接依赖，并验证目标 Mixin 在 `Main` 中的 MRO、属性和辅助方法均可用。

2. **多入口行为一致性规则**  
   对命令、WebUI、后台任务等多个入口，确认其最终调用同一个业务方法，并比较权限、审计、状态更新和异常处理差异。

3. **副作用流程原子性规则**  
   对“撤回 + 禁言 + 学习 + 状态更新”这类链路，必须检查每一步失败后的状态、重试行为和重复点击幂等性。

4. **远程高风险操作规则**  
   WebUI 迁移或新增处罚方法时，必须确认权限校验、二次确认、双管理员审批、审计日志均位于不可绕过的调用链上。

5. **测试证据分层规则**  
   “模拟 Mixin 组合测试通过”应与真实路由测试、权限失败测试、平台操作失败测试区分，不能将模拟测试等同于端到端验证。

6. **配置/常量变更规则**  
   即使只修改一行常量，也应说明旧值、新值、已有数据库或历史状态的兼容性影响。

项目特有规范可补充为：

> 任何面向 WebUI 的远程审核动作，应优先定义在 Web 业务层或独立审核服务层；命令入口只能委托，不应保留另一份处罚实现。

## 4. 经验教训

- 看到“某类没有某方法”时，不能只检查方法定义是否存在，还要检查**实际实例类型和 MRO**。
- Mixin 项目中，文件归属不等于运行时能力归属；应同时检查定义位置、继承清单、调用者和依赖。
- 删除重复代码是好方向，但必须验证删除后命令入口仍然可用，特别是项目明确采用“命令显式委托”的情况下。
- 对远程确认类功能，成功路径不是唯一重点，应额外检查：
  - 重复确认是否幂等；
  - 撤回失败但禁言成功时如何记录；
  - 禁言失败是否仍标记为已确认；
  - 学习成功但处罚失败是否允许重试；
  - 操作人权限在确认时是否重新校验。
- “448 项通过”应进一步区分单元测试、集成测试、路由测试和真实平台冒烟测试，避免测试数量造成过度信心。
