## 1. 审查质量评估

### 覆盖度

本次审查抓住了两个核心控制流问题，覆盖了新功能的主路径：

1. **统一审核路径不可执行**  
   `_submit_ad_review` 含有 `yield`，实际类型是异步生成器；调用方使用 `await` 属于确定性错误。该问题会直接阻断 `ad_review_enabled=True` 时的视频入队、通知和后续统一审核流程。

2. **视频广告信号导致审核链路提前终止**  
   当统一审核和旧视频审核均关闭时，调用方仍无条件 `return`，会导致视频广告检测命中后跳过后续链接、规则和 LLM 审核。这不是简单的“视频不处理”，而是可能造成审核开天窗。

但从变更意图和描述看，仍有若干值得补查的风险：

- `_submit_ad_review` 的异步生成器结果是否必须逐项 `yield` 转发，还是只需消费副作用；
- 统一审核与旧流程之间是否存在**重复入队、重复通知或重复处罚**；
- `source="video"` 是否在数据库、WebUI、确认接口和统计接口中都能正确展示和处理；
- 后台确认后按 `msg_id` 撤回视频的行为是否受消息平台撤回窗口限制。项目记忆中 OneBot 撤回窗口约为 2 分钟，视频审核可能远晚于该窗口；
- 视频消息的 `msg_id` 是否稳定、唯一，是否可能为空或无法用于后续撤回；
- “学习文本与视频指纹”是否只在确认后发生，放行、重复确认、撤回失败时是否会错误学习；
- 配置开关从旧版流程切换到统一流程时，群级配置和默认值是否保持兼容；
- 统一审核日志的待处理状态是否具备幂等性，重复检测同一个视频时是否会生成重复记录。

因此，当前审查对直接回归问题覆盖较好，但对“统一审核闭环”和“兼容旧流程”的数据、状态及异步副作用覆盖不足。

### 准确度与严重程度

两个 `major` 基本合理：

- 异步生成器错误是**确定性运行时异常**，只要开启统一视频审核即可触发，属于核心新功能完全不可用。
- 无条件 `return` 会绕过其他审核规则，影响范围取决于视频广告检测命中率，但其结果是潜在漏审，符合项目记忆中“审核绕过、漏报倾向 high”的判断。

可以进一步区分影响：

- 第一个问题更接近“功能完全失效”，应保持 `major`；
- 第二个问题属于审核链路绕过，若确认调用位置位于统一审核入口且后续规则本应继续执行，也应保持 `major`。若该 `return` 只发生在视频专属处理函数、调用方仍有统一兜底，则严重程度可能降为 `minor/medium`，需要通过调用链确认，不能仅凭函数片段最终定级。

评论提出的修复方向是正确的，但还应提醒：

```python
async for item in self._submit_ad_review(...):
    yield item
return
```

这里的 `return` 只应位于“确实已经将消息交给统一审核、无需继续执行其他审核”的分支中；对于两个开关都关闭的分支，应改为继续返回调用方，而不是直接终止整个审核链。

### 测试完整性

新增测试使用普通 async coroutine stub，未模拟真实异步生成器，是本次回归的关键测试缺口。测试虽然“448 项全过”，但没有验证真实接口协议，说明测试更偏行为断言，缺少调用约定验证。

至少应补充：

- 使用真实 `_submit_ad_review` 或 async generator stub；
- `ad_review_enabled=True` 时验证能成功入队、通知，并无 `TypeError`；
- 两个开关均关闭时，验证链接、规则、LLM 审核仍被调用；
- 两个开关分别开启时，验证只进入对应流程且不重复处罚；
- 重复视频、确认/放行、撤回失败等状态转换测试。

## 2. 发现的代码与架构模式

### 代码模式

- 项目大量通过配置开关切换新旧流程，容易出现“入口分支已切换、旧流程仍提前返回”的控制流问题。
- 异步生成器被用作既执行副作用、又向上层传递事件的接口。这种接口比普通协程更容易被错误 `await`。
- 测试倾向于通过 stub 替换内部方法，若 stub 的返回协议与真实实现不一致，会掩盖 `await`/`async for` 类型错误。
- 视频审核涉及下载、抽帧、OCR、视觉识别、指纹及人工审核，属于多阶段流水线。当前新增逻辑把“检测结果路由”和“处罚/学习”关联在一起，状态边界需要特别清晰。

### 架构观察

- 审核链路是“自动初筛 → LLM → 处罚/人工复核”的多入口架构，文本、图片、群名片、视频逐步汇入统一日志。
- `ad_review_enabled` 同时承担流程选择和兼容旧版行为的职责，容易产生配置组合矩阵问题。至少存在：
  - 统一开；
  - 旧视频流程开；
  - 两者都开；
  - 两者都关；
  - 群级覆盖与全局默认组合。
- 视频消息后续动作依赖平台能力，尤其是撤回和禁言；后台人工确认天然存在延迟，因此不能假设检测时保存的 `msg_id` 一定可在确认时成功撤回。
- `ad_reviews` 可能成为多个消息类型共用的状态中心，建议明确 `source`、原始消息元数据、处理状态、处罚状态和学习状态，而不是仅依赖 `msg_id` 判断流程。

## 3. 规范完善建议

建议新增或强化以下审查规则：

1. **异步接口协议必须按真实实现审查**  
   对包含 `yield` 的函数，明确标记为 async generator；调用方必须使用 `async for`，测试 stub 也必须保持相同协议。可增加静态检查或单元测试断言：
   ```python
   inspect.isasyncgenfunction(...)
   ```

2. **审核分支必须覆盖所有开关组合**  
   对两个及以上相关配置开关，要求测试完整组合，尤其是“全部关闭”分支必须证明不会绕过后续通用审核。

3. **审核链路禁止无依据提前 return**  
   审查应区分：
   - 当前消息已被某流程接管，可以终止；
   - 当前流程未启用，只是没有处理，需要继续后续审核。
   
   建议在代码中使用显式结果，例如：
   ```python
   handled = await/async_process(...)
   if handled:
       return
   ```

4. **统一审核必须验证状态闭环**  
   对“入队 → 通知 → 确认/放行 → 撤回/处罚 → 学习”的每一步检查幂等性、失败处理和状态持久化。

5. **人工审核与平台时效必须联动审查**  
   对视频、图片等后台审核对象，必须检查撤回窗口、消息 ID 持久化、撤回失败后的降级动作和管理员提示。

6. **测试替身不得改变异步语义**  
   mock/stub 应保持真实函数的返回类别、异常类型和迭代行为，不能用普通 coroutine 代替 async generator。

项目特有规范还应明确：统一审核确认后才允许学习文本或视频指纹；“放行”不得学习为广告；处罚失败不得被误标为已完成。

## 4. 经验教训

- 看到 `async def` 不能默认使用 `await`；只要函数包含 `yield`，就必须按异步生成器审查。
- “测试全部通过”不能替代接口协议验证，尤其是 mock 覆盖了真实实现时。
- 配置兼容改造最容易在默认关闭路径上产生漏审：新功能关闭不应意味着消息退出整个审核管线。
- 对审核系统而言，漏审通常比单个功能异常更危险。所有提前返回都应回答：**消息是否已经被另一个可靠流程接管？**
- 视频人工审核不能只关注“是否写入日志”，还要验证确认时是否仍能撤回，以及撤回失败是否有明确、可审计的结果。
- 统一日志不只是数据汇总，还承担流程状态管理；不同来源接入时必须统一字段语义和状态转移。

### 是否引入新风险

此外还可能引入：

- 统一日志确认后的撤回时效问题；
- `source=video` 在后台接口、数据库和状态处理中的兼容问题；
- 确认、放行、学习和处罚之间的重复执行问题。

### 增量范围造成的覆盖下降

本次只新增 1 个提交，容易只检查新增的 25 行路由代码和测试断言，而忽略其依赖的真实 `_submit_ad_review` 实现、调用方审核顺序、后台确认接口及旧版视频流程。尤其是测试新增的是“路由断言”，没有覆盖真实异步调用和端到端状态闭环。

后续增量审查应至少沿调用链向两侧扩展：

- 向上：谁调用 `_route_video_ad_review`，其 `return` 是否终止整个审核流程；
- 向下：`_submit_ad_review` 如何写库、通知和生成结果；
- 横向：后台确认、放行、撤回、禁言、指纹学习是否支持 `source=video`；
- 兼容性：旧开关、群级覆盖和默认关闭行为是否仍与 v2.23.0 一致。

总体而言，本次审查结论可靠，`request_changes` 和 4/10 基本匹配；但若要达到完整审查标准，还应补充异步协议、开关组合、重复处理和人工审核状态闭环方面的验证。
