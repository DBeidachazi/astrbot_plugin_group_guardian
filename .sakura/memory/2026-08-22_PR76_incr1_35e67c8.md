## 2. 发现的模式

### 代码模式

从变更规模和项目记忆可推断出几个值得关注的编码模式：

- 同步客户端承担了较多职责，可能同时负责鉴权、数据序列化、推送、拉取、Actions 和审计日志处理。
- 安全约束主要通过字段过滤和测试固化，而不是由统一的数据传输对象或显式 allowlist 在架构层保证。
- 审计日志与广告复核状态存在关联，容易出现“业务动作成功但审计记录失败”或“日志已同步但业务状态未同步”的不一致。
- 大量删除和新增表明可能存在逻辑重排或接口重构。此类改动即使最终行为看似不变，也容易改变异常处理、默认值、重试和兼容行为。

### 架构观察

项目具有以下架构特点：

- 本地插件业务、SQLite 状态、外置词库和远程同步服务并存。
- 审核动作具有明显副作用：撤回、禁言、踢人、学习和人工复核。
- 审计日志不是普通附属数据，而是安全闭环的一部分，需要能回答“谁在何时对哪条审核记录执行了什么动作，以及动作是否成功”。
- `sync_client.py` 依赖 `astrbot.api`，说明同步客户端可能与运行时框架耦合。需要警惕在非 AstrBot 环境、测试环境或初始化不完整时导入/调用失败。

## 3. 规范完善建议

建议新增或强化以下审查规则：

1. **同步重构必须进行协议级审查**  
   只要同步客户端发生大规模增删，即使提交是增量，也必须检查：
   - 请求和响应字段；
   - 新旧版本兼容；
   - 空值、缺失字段和未知字段；
   - 超时、重试、重复请求和部分失败。

2. **敏感字段必须采用正向 allowlist**  
   不应只依赖“排除已知密钥字段”。应明确每个同步对象允许传输的字段，并测试未知敏感字段不会被自动带出。

3. **审计日志同步必须验证完整性和不可抵赖性**
   至少检查：
   - 唯一 ID；
   - 操作者和目标对象；
   - 动作前后状态；
   - 成功/失败结果；
   - 时间戳；
   - 重试是否产生重复日志；
   - 日志是否可被普通同步覆盖或删除。

4. **双向同步必须声明权威来源和冲突策略**  
   对每种实体明确“本地优先、远端优先、按版本、按时间，或冲突拒绝”，不能隐含依赖字典覆盖、列表顺序或最后写入。

5. **增量审查不得只看文件名和摘要**  
   对大规模单文件改动，应以提交 diff、父版本行为、调用入口和相关测试为依据，不能因为 PR 只有一个新提交就降低审查深度。

6. **测试证据应区分安全和功能**
   `no_secrets` 测试只能证明部分字段未泄漏，不能替代：
   - 双向同步测试；
   - 旧版本兼容测试；
   - 重试幂等测试；
   - 数据库失败和网络失败测试；
   - 并发同步测试；
   - 审计闭环测试。

项目特有规范还应补充：审计日志与审核状态必须共享稳定关联 ID；所有同步动作应记录结果但不得记录凭据、完整消息内容或未经脱敏的第三方响应。

## 4. 经验教训

未来审查类似变更时，应优先关注：

- **字段边界**：新增 `audit_logs` 是否意外携带上下文对象、配置对象或请求头。
- **状态边界**：审计日志同步失败时，主业务动作是否仍被判定成功；重试时是否重复处罚。
- **数据边界**：远端拉取的数据是否未经校验就覆盖本地状态，是否可能导致旧审核结果恢复。
- **身份边界**：同步接口使用的凭据是否与用户自建服务器密码混用，日志是否暴露认证信息。
- **异常边界**：网络异常、JSON 解码失败、字段缺失、服务端返回 4xx/5xx 时，是否有明确处理和可恢复状态。
- **兼容边界**：v2.36.10 与旧客户端、旧服务端、旧数据库结构之间是否能互操作。
- **调用边界**：命令、WebUI、后台任务是否都经由同一同步方法，避免某个入口漏掉鉴权、脱敏或审计。

尤其要避免把“测试文件存在”当成“功能已被充分验证”。应查看测试是否覆盖真实调用路径，而不是只测试纯函数或 mock 返回值。
